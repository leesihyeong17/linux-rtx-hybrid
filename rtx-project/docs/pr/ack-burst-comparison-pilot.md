# 묶음 전송 사이에 수신 확인을 기다릴 때 TCP 재전송 큐의 비용

**공동 시험 질문**　한 연결에서 32 KiB씩 보내고 상대가 그 묶음을 다 읽으면 다음 묶음을 보내는 프로그램을 가정한다. 이때 송신 중인 데이터가 최근 LIST의 용량(K=16) 안에 머물러 승격이 줄어드는가? 같은 프로그램을 원래 V3(RB+TAIL)와 V4(하이브리드+TAIL)에서 실행하면 수신 바이트당 CPU 시간도 줄어드는가?

예를 들면 다음 블록을 보내기 전에 수집기의 수신 확인을 기다리는 로그 전송 방식이다. 이 시험은 한 호스트 안의 TCP 연결로 그 **전송 규칙**을 재현한다. 실제 로그 서비스의 트래픽 비중이나 물리 NIC 성능은 별도로 확인할 사항이다. 삽입·삭제 구현은 그대로 두었다. 보류된 ACK prefetch 변경은 소스에서 철회했고 당시 이미지와 기록은 보존했다.

## 친구의 측정에서 가져온 근거

| 커널 연산과 큐 상태 | V3 → V4 묶음 시간 | 부팅 안 중앙값 기준 변화 | 같은 원자료의 부팅 안 평균 기준 변화 |
| --- | --- | ---: | ---: |
| 오래된 순서로 64개 삭제, N=64→0 | 333 → 292 ns | −12.3% | −4.7% |
| 가득 찬 LIST의 끝에 32개 추가, N=64→96 | 125 → 208 ns | +66.4% | +39.3% |
| 큐 중앙의 빈 구간에 32개 삽입, 양쪽 모두 TREE에 삽입 | 625 → 625 ns | 0.0% | +1.4% |

삭제는 40쌍 중 33쌍에서 V4가 빨랐고, 끝 삽입은 별도 40쌍 모두에서 V4가 느렸다. vfkit 게스트의 24 MHz 타이머에서 한 눈금은 41.67 ns다. 코드는 묶음 시작과 끝에서 시각을 한 번씩 읽었다. 대표 삭제 시간은 8눈금에서 7눈금으로 바뀌었다. 큐가 짧은 상황에서의 삭제 비용은 따로 재야 한다. 64개 삭제에는 TREE와 LIST 양쪽이 포함됐고, 커널은 미리 알고 있던 포인터들을 분리했다. 실제 ACK 처리의 순회·회계·해제는 이 시간에 포함되지 않았다. [친구의 최신 측정과 타이머 진단](https://false-resolution-beb.notion.site/TCP-ARM64-40-423daacb8cd4810f8f75c2c5cd86c104)

기존 팀 공용 VM의 일반 무손실 TCP 10쌍에서 V4의 CPU ns/B 변화는 −2.13%, 95% 구간은 −3.70%~+4.62%였다. 이 결과와 RB 기본값 유지 결론을 함께 보고한다. 이번 질문은 전송 방식에 따라 손익이 달라지는지에 한정한다. [기존 비교 조건](https://github.com/leesihyeong17/linux-rtx-hybrid/issues/30#issuecomment-7118672937) · [별도 ARM64 VM 결과](https://github.com/leesihyeong17/linux-rtx-hybrid/pull/38)

## 11월 25일 로컬 실행 결과

QEMU 4.2.1 TCG(ARM64, 1 vCPU, 448 MiB)에서 원래 V3와 V4를 한 번씩 부팅했다. 두 커널 모두 두 조건에서 2,097,152바이트와 번호가 맞는 수신 확인 64개를 검증했다. 네 전송 모두 받은 바이트의 SHA-256은 `91d3beb88a9b2f778a6c44a1c53b63d3c79931845a9aef84b3fb414610bd1938`이었다. 첫 게스트의 Python 스레드 실행에 필요한 `libgcc_s.so.1`이 initramfs에서 누락됐다. 라이브러리를 포함한 뒤 다시 부팅해 통과했다. 커널 빌드와 팀 VM 재부팅은 없었다.

별도 #28 STATS v2 이미지(`18060408b`)로 QEMU 게스트를 세 번 새로 부팅했다. 실행 순서는 대기→연속, 연속→대기, 대기→연속이었다. 포트 5001을 양방향으로 관찰한 값이다.

| 독립 부팅 | 전송 | 승격 / 전체 삽입 | ACK 시작 시 N≤16 | 완전 삭제 수 / ACK 정리 호출 |
| --- | --- | ---: | ---: | ---: |
| 1 | 대기 | 0 / 583 | 100% | 583 / 261 = 2.23 |
| 1 | 연속 | 51 / 532 | 97.84% | 532 / 231 = 2.30 |
| 2 | 대기 | 0 / 583 | 100% | 583 / 261 = 2.23 |
| 2 | 연속 | 76 / 550 | 97.83% | 550 / 230 = 2.39 |
| 3 | 대기 | 0 / 583 | 100% | 583 / 264 = 2.21 |
| 3 | 연속 | 68 / 568 | 96.92% | 568 / 227 = 2.50 |

세 번 모두 대기 조건은 승격이 0회였고, 연속 조건은 삽입의 9.6~13.8%에서 승격이 일어났다. 같은 바이트 수에서도 TCP가 만든 skb 수가 달랐다. 대기 조건의 호출당 삭제 수는 오히려 더 작았다. 따라서 다음 검증의 초점은 **승격 횟수 차이가 같은 전송 방식에서 V3 대비 V4의 CPU 비용에도 영향을 주는지**다. 이 세 부팅은 소프트웨어 에뮬레이션이며 관측 커널 SHA도 성능용 이미지와 다르다. 팀 VM에서 현재 실행 중인 별도 `ack-head` 이미지에서도 전송만 확인했고, 각 실행에서 VM CPU 시간은 1틱뿐이었다. 여기서 실제 ARM64의 성능 개선율을 정할 수 없다.

공유 ZIP의 `evidence/`에 각 부팅의 manifest, 실행 명령, 시리얼 로그, 조건별 JSON, STATS 원본과 초기 실패 로그가 있다. 저장소 로컬 원본은 `rtx-project/.work/ack-burst-pilot-GJpkHm5c/`, 호스트 기능 확인은 `rtx-project/.work/burst-native-smoke-DT7psJsF/`에 보존했다.

## 둘이 바로 해 볼 시험

각자 **Linux VM**에서 ZIP을 빈 폴더에 풀고, `rtx-project/`가 보이는 위치에서 실행한다. 기존 저장소를 사용하면 저장소 최상위에서 실행한다. Python 3.8 이상, 로컬 IPv4와 사용 가능한 TCP 포트 5001이 필요하다. 일반 사용자 권한으로 가능하다.

```bash
(
  set -eu
  out=$(mktemp -d "$PWD/burst-test-XXXXXXXX")
  echo "$out"
  for pattern in gated continuous; do
    python3 -B rtx-project/tests/runtime/tcp_burst_pilot.py "$pattern" \
      --groups 64 --chunks-per-group 8 --chunk-bytes 4096 --port 5001 \
      > "$out/$pattern.json" 2> "$out/$pattern.stderr" || { cat "$out/$pattern.stderr" >&2; exit 1; }
    cat "$out/$pattern.json"
  done
)
```

| 조건 | 송신자 동작 | 두 조건의 공통 입력 |
| --- | --- | --- |
| `gated` | 4 KiB를 8번 쓴 후 상대의 응용 수신 확인을 기다린다. | 같은 연결에서 64묶음, 쓰기 512회, 2 MiB |
| `continuous` | 다음 묶음을 곧바로 보내고 별도 스레드로 수신 확인을 읽는다. | 수신자가 매 묶음마다 같은 8바이트 번호를 회신한다. |

성공은 두 JSON 모두 `status=PASS`, `sent_bytes=received_bytes=2097152`, `receipts_validated=64`, 송수신 SHA-256 일치다. 4 KiB는 응용 쓰기 크기이고 32 KiB는 응용 묶음 크기다. TCP는 쓰기를 합치거나 나눌 수 있고, 응용 수신 확인과 TCP ACK도 별개다. 첫 출력의 `boot_id`, `build_id`, `pattern`도 함께 보관한다. 임의 커널에서 위 명령을 실행하면 연결과 데이터 검증 단계까지 확인할 수 있다.

## 승범과 친구가 각각 확인할 것

**승범 — 실제 큐가 어떻게 달라지는지 확인.** 먼저 팀 VM에서 설치된 `5.4.214-d30-hybrid-tail-n-distribution-k16-18060408`을 선택한다. 이 관측 커널은 DEBUG off, STATS v2 on이다. 다른 5001번 트래픽을 멈추고 아래 블록을 실행한다. 포트 필터는 VM 전체에 적용되므로 블록이 끝날 때 직전 값으로 복원한다. 독립 실행을 더 할 때는 두 조건 순서를 바꾸고 새 출력 폴더를 쓴다.

```bash
(
  set -eu
  out=$(mktemp -d "$PWD/burst-stats-XXXXXXXX")
  old=$(awk '$1 == "filter_port" {print $2}' /proc/rtx_stats)
  test -n "$old"
  sudo -v
  trap 'printf "port %s\n" "$old" | sudo tee /proc/rtx_stats >/dev/null' EXIT
  printf 'port 5001\n' | sudo tee /proc/rtx_stats >/dev/null
  echo "$out"
  for pattern in gated continuous; do
    python3 -B rtx-project/scripts/observe_tcp_burst.py "$pattern" \
      --output "$out/$pattern" --port 5001 \
      --expect-build-id f8370cc8df3b9ed9a05e0b47beaca81d7fa0a6cb
  done
)
```

위 build ID는 팀 VM용이다. 친구가 자체 빌드한 경우 각 이미지의 원본 `vmlinux`에서 `readelf -n /경로/vmlinux | grep 'Build ID'`로 대조한다. 관측 결과는 전후 원본 `before.txt`, `after.txt`, 전송 결과 `workload.json`, 판정 `status.json`이다. `n_le_k_fraction.n_ack.16`은 ACK 정리 진입 때 N≤16인 비율(0~1), `counters.promote / insert_samples`는 삽입당 승격 횟수, `ack_unlink / ack_clean`은 정리 호출당 완전 삭제한 skb 수다. 데이터와 역방향 응답, 연결 시작·종료까지 양쪽을 합산한다. 포트 오류, 커널 불일치, 카운터 불일치, 전송 실패를 기록한 실행은 표본에서 제외하고 원본을 남긴다.

**친구 — 노션에서 확인한 삭제 이득을 이번 큐 길이에서 재기.** N=4·8·16에서 큐를 비우는 케이스와 기존 N=64 재현을 각각 둔다. N=64 포화 끝 삽입도 대조로 보존한다. 동일한 N의 독립 큐를 여러 개 미리 준비하고, 타이머 시작과 끝을 한 번만 읽어 모두 처리한다. 한 큐의 N을 64에서 수천으로 키우면 다른 연산을 재게 된다. 예비 실행으로 더 빠른 구성에서도 묶음당 적어도 100눈금이 되게 큐 수를 정한 뒤 양쪽에 동일하게 적용한다. 항목당 시간의 분모는 실제 처리 큐 수 × 큐당 처리 항목 수다.

skb와 포인터 배열은 시간 구간 밖에서 할당하고, 기존 삽입 fixture의 1,072 B 스택 프레임 경고도 배열을 스택 밖으로 옮겨 재검사한다. 각 큐의 시작 순서·삭제 수·최종 빈 상태를 검증한다. 사전 조회 4,096회 유무는 다른 조건으로 기록하고, 동일 조건 안에서 V3·V4를 비교한다. 원시 묶음 ns, 시계 주파수, 부팅 ID, 큐 수, 워밍업 제외 기준, 실패를 공유한다. 이 절차는 친구의 fixture 후속 실험 제안이며 이번 ZIP의 Python 명령은 실제 TCP를 실행한다.

**두 사람이 함께 — 실제 CPU 이득 확인.** 먼저 각자 자신의 VM에서 V3와 V4 한 쌍만 예비 실행한다. 한 사람이 V3, 다른 사람이 V4만 재면 VM 차이를 분리할 수 없다. 팀 VM에서는 아래 이미지가 이미 설치돼 있고 같은 GCC 9.4, 소스 `f78f5626ab0c307050f25b50606a61a104de6dac`, CACHE·TAIL on, DEBUG·STATS off다.

| 팀 VM에서 선택할 일반 부팅 항목 | 시험에 지정할 GNU build ID |
| --- | --- |
| V3 · `5.4.214-d30-rb-tail-tcp-k16-f78f5626` | `1e8716d3ed7174c595f3522c31747c29335d4b3a` |
| V4 · `5.4.214-d30-hybrid-tail-tcp-k16-f78f5626` | `3d509760a828e60d828ee8230854e9acb579970a` |

팀 VM에 남은 `-ack-head` 실험 이미지는 원래 V4와 `uname -r` 문자열이 같다. 각 부팅에서 첫 예제의 Python 명령 끝에 `--expect-build-id 위_표의_해당_ID`를 추가하면 다른 이미지에서 실행할 때 전송 전에 멈춘다. 친구는 자기 이미지 두 개의 build ID와 config 해시를 기록한다.

1. 두 전송 규칙 모두 같은 바이트·묶음 크기를 유지한다. 본 측정 전에 예비 실행으로 `--groups`만 늘려 더 짧은 실행도 예를 들어 10초 이상, VM busy 100 ticks 이상이 되게 한다. 그룹 수를 고정하고 예비 실행은 본 표본에서 뺀다.
2. 본 측정을 진행하면 각 VM에서 독립 부팅 10쌍을 미리 정한다. 홀수 쌍은 V3→V4, 짝수는 V4→V3다. 부팅 후 같은 시간(팀 기존값 45초) 대기하고 두 방식 모두 한 번씩 예열한다. 한 쌍 안에서는 두 커널의 전송 규칙 실행 순서를 맞추고, 다음 쌍에서 뒤집는다. 원시 JSON을 호스트·쌍·커널·조건별로 보존한다.
3. 주 지표는 `vm_busy_ticks × 1e9 / clk_tck / received_bytes`이며 단위는 ns/B다. 시간 구간은 수신자가 데이터 전송 시작을 알리기 직전부터 마지막 EOF까지다. VM CPU에는 해싱·Python·스케줄링도 포함된다. 처리량은 `goodput_mbps`다. 환경별로 gated의 V4/V3를 먼저 보고, 같은 방식으로 continuous와의 효과 차이를 본다. 쌍별 변화율은 `100 × (V4/V3 − 1)`, 요약은 중앙값과 쌍 단위 부트스트랩 95% 구간(10,000회, 시드 16)이다.
4. 기존 제안 기준을 이어 쓰면 gated CPU 중앙값 −3% 이하에 구간 상한 <0%, 처리량 구간 하한 ≥−2%가 필요하다. 64 B 요청·응답 p99 구간 상한 ≤+5%는 별도 기존 RR 시험에서 잰다. 이 스크립트는 RR p99를 산출하지 않는다. 탐색 뒤 조건을 바꾸면 새 가설과 새 독립 표본으로 표시한다. UTM, vfkit, QEMU TCG 표본은 각각 보고한다.

어떤 ACK가 여러 항목을 완전히 비웠는지까지 주장하려면 관측용 커널에서 **같은 데이터 송신 소켓의 정리 호출마다** 진입 시 큐 길이 N, 완전히 삭제한 수 B, 종료 시 잔여 큐 길이를 함께 기록해야 한다. 부분 trim은 B에서 제외하고 B=0도 남긴다. 같은 범위의 전체 호출 수와 B의 합을 각각 `ack_clean`, `ack_unlink`와 대조한다. 현재 히스토그램과 합계만으로는 이 결합 분포를 복원할 수 없다.
